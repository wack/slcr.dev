A requirement is a statement about the desired state of the source code.
Validators are how SLCR tests that statement.
Each validator runs a tool, such as a test runner, a linter, or a
script, and reports green or red. `slcr check` runs them all and combines
their results through the spec's
[links](/docs/concepts/links-and-satisfaction) into a status for every
requirement.

The chain from a requirement to a result looks like this:

1. A **requirement** states what must hold.
2. Its **acceptance criteria** say what "done" looks like.
3. **Validators** name a criterion and the tool that proves it.
4. A **tool descriptor** says how to run that tool.
5. `slcr check` runs the tools and reports what's satisfied.

## Acceptance criteria

An acceptance criterion describes, for one requirement, what someone could
check to know the requirement holds:

```yaml
acceptanceCriteria:
  - kind: acceptanceCriterion
    id: AC-001
    title: Table schema is declared
    body: >-
      A table named `todo_list_item` is declared with a string column `title`
      and a boolean column `done`. A structural match against the schema or
      migration source is sufficient.
```

Criteria are written before the code exists, so they name no files,
functions, or code patterns. They describe behavior, and leave how it's
checked to validators. A criterion asserts nothing on its own: the
requirement is the claim, and validators prove it. A requirement doesn't need
criteria to be valid, but criteria make it much easier to see what a
validator should check.

## Validators

A validator is an entry in a validator file, which sits in the directory of
the code it checks:

```toml
# src/views/items/.validators.slcr.toml
formatVersion = "1"

[[validator]]
requirement = "todo-api/REQ-002"
criterion = "AC-004"
tool = "ast-grep"
description = "POST handler is defined and registered with the router"
with = { rule = "rules/post-handler.yml" }

[[validator]]
requirement = "todo-api/REQ-002"
tool = "cargo-nextest"
with = { test = "items::post::creates_item" }
```

Each validator names:

- the **requirement** it checks, qualified with the spec's name, even in a
  project with only one spec
- optionally, the **criterion** it proves, which must belong to that
  requirement
- the **tool** that runs the check, which must be declared in `SLCR.toml`
- the tool's settings, under **`with`**

Validator files are named `.validators.slcr.toml`, `.yaml`, `.yml`, or
`.json`, with at most one per directory. `slcr` finds them by walking the
project and skips git-ignored paths. Because a validator file sits beside the
code it checks, it moves with that code.

### The dependency runs one way

Validators name requirements, and requirements never name validators. The
spec says what must be true and stays readable for anyone, including people
who never look at the code. All the implementation detail, such as test
names, file paths, and tool settings, lives with the code. You can rewrite
the tests without touching the spec, and edit the spec without knowing how
it's tested.

### Several validators per criterion

Turning an acceptance criterion into validators is called materializing it.
One criterion may need several validators. For example, the same
authentication check might need to run against handlers in two directories.
A requirement's own validators are ANDed: every one must pass for the
requirement to be satisfied.

A validator only proves something if it can fail. The usual loop is
red-green: write the validator, watch it fail before the code exists, then
implement until it passes.

## Tools and descriptors

SLCR has no built-in tools. Each project declares the programs its
validators may run, and a **tool descriptor** says how to run each one:

```toml
formatVersion = "1"
name = "cargo-nextest"
version = "1.0.0"

[validator.schema]
type = "object"
required = ["test"]
additionalProperties = false
properties.test = { type = "string", minLength = 1 }

[invoke]
argv = ["cargo", "nextest", "run", "--no-tests=fail", "-E", "test(={with.test})"]
cwd = { nearest = "Cargo.toml" }

[results]
pass = [0]
```

A descriptor is a small, declarative TOML file. It's never executed itself
and never run through a shell. It gives:

- the **schema** that every validator's `with` must satisfy, so a typo in a
  validator is caught before anything runs
- the **command**, as an argument list. Placeholders like `{with.test}` are
  filled from the validator.
- the **working directory**: the project root, the validator's directory, or
  the nearest directory containing a given file. It can also set an
  environment and a timeout.
- the **exit codes** that count as a pass. Any other exit code, a signal, or
  a timeout is red.

A descriptor can wrap anything, including a short script committed to the
repository, so validators can check whatever a program can check: tests,
code structure, configuration, or generated files.

### Pins

`slcr tools add` declares a tool in `SLCR.toml`, recording where its
descriptor came from and a **pin**: the BLAKE3 hash of the descriptor's
exact bytes. A descriptor's source is either a path inside the project or an
`https://` URL. `slcr` refuses to use a descriptor whose bytes don't match
its pin, so the commands that run on a machine are always the ones reviewed
in the manifest's history. Pins are written only by `slcr tools`, never by
hand.

Installed descriptors live in a store in `slcr`'s data directory, filed by
pin and shared by every project on the machine. On a fresh clone,
`slcr tools install` fills the store with exactly what the manifest pins.
After that, vetting and checking need no network.

## Vet and check

The two words have fixed meanings in SLCR:

- **`slcr vet`** asks whether the project is well formed: specs, validator
  files, the manifest, and installed descriptors. It finds broken links,
  cycles, duplicate IDs, and validators whose `with` doesn't match their
  tool's schema. It runs nothing and never uses the network.
- **`slcr check`** asks whether the validators pass. It installs any missing
  descriptors (unless `--offline`), vets the project, and runs nothing if
  vetting fails. Then it runs every validator in parallel and reports each
  requirement's status.

A validator's result is one of:

| Result | Means | What to do |
| --- | --- | --- |
| Green | The tool ran and passed | Nothing |
| Red | The tool ran and failed | Fix the code, or fix the validator if it's wrong. Don't loosen the requirement to get green. |
| Could not be run | The tool couldn't start, for example because it's missing from `PATH`. It proves nothing either way, so `check` fails. | Fix the environment, not the code |

`slcr check` prints the end of a red validator's output under its status
line, and `--format json` includes all of it.

Running `slcr check` means running the commands a project's descriptors
declare, just as running a test suite means running its tests. Only check
repositories you trust.
